How experiments lie

Every number in this project had a way to be wrong that would not have thrown an error. This page is the catalogue: each lie, the real instance of it that happened here, and the check that now stands where it happened.

The one idea on this page
A measurement pipeline does not fail loudly. It returns a plausible number computed the wrong way, and the number ends up on a slide. The defence is not "be careful" — it is to name each specific way a number here could lie, and stand a check on that exact spot. The harness (src/verify.py plus a 19-test suite) is precisely that: a list of named lies, each with a guard. And even so, an adversarial re-audit that recomputed every number from the raw prediction files found nine more the automated checks never saw — including a passing test whose fixture was too weak to exercise the very bound it claimed. Automation catches the lies you have already met. The audit is for the ones you haven't.

Two layers that run before anyone believes a table

Nothing on the harness page is trusted until two things pass. Neither touches the GPU; both run in seconds.

src/verify.pyArtifact self-consistency. Walks every runs/predictions/*.npz and its JSON sidecar and asserts they agree with the manifest, with each other, and with git. Exit non-zero on any mismatch, so it sits in the pre-flight. Its docstring opens: "run it before you believe any table." 19-test suite9 metric-invariant tests (tests/test_metrics.py) + 10 attack-property tests (tests/test_attacks.py). No GPU, no data, no network. Claimed <2 s; measured 2.48 s in pytest.

The interesting thing about verify.py is that its docstring is a confession. It lists four defects that "actually happened in this repo, silently, and were caught by a reviewer rather than by the code." Each bullet below is now a check. That is the whole method: a lie is only defended once it has been told.

A subtle design point in the guard itself
The uid check is on the per-split uid sequence, not on a hash of the whole manifest file. manifest_v1 and manifest_v2 have byte-identical calib and test uid sequences and differ only in fit — because WP3 enlarges the training set while every reported number stays on the same held-out slice. A whole-file hash would reject exactly the comparison the project needs and catch nothing real. The naive strong check is both too strict and useless; the right check is narrower and pointed.

The case files

Nine ways this project's numbers could have lied, each with its real example. Some were caught by the two layers above. The ones marked audit only were not — they were found by a human recomputing from the .npz.

1 · Leakage — splitting on a key that isn't one

The lie: your test set is in your training set, and nothing says so
The archetypal version is splitting a corpus by document when the label lives at the company level, so the same company appears on both sides. Here the concrete near-miss is img_id. It looks like a unique identifier. It is not: the synthetic and tampered classes are numbered sequentially and the counter restarts per split, so 19,107 img_ids appear in both train and validation — 10,000 synthetic and 9,107 tampered. Every one of the 10,000 fully-synthetic validation images shares its img_id with a train image. Zero reals collide. (runs/img_id_collisions.json: train 210,000 unique, validation 30,000 unique.)

How it was avoided: the harness splits on uid, the genuinely unique key. manifest_v1 has uid unique, fit drawn only from train:, calib (4,684) and test (15,316) drawn only from validation:. Had anyone split on img_id thinking it a key, the whole result would have leaked. audit note the old README quoted 8,634 collisions — a hard-coded integer literal at src/manifest.py:171 that no code ever computed. The audit recounted all 283 shards: the true figure is 2.2× larger. See the dataset page.

2 · The dataset shortcut — a rule with no model that beats the model

The lie: 0.93 accuracy that is really 0.93 accuracy at reading image dimensions
On this split, the rule "width == height → fake" — no network, no pixels — scores 0.9785 (runs/trivial_baselines.json, majority class 0.5000). It works because 100% of synthetic and 100% of tampered images are square 1024×1024, and only 4.30% of reals are. A detector reporting 0.83 is below a one-line if statement. Reading that 0.83 against 0.5 instead of against 0.9785 would have told a story exactly backwards.

How it is caught: src/baselines.py computes the trivial baselines and the ACE condition table now prints, in bold, "read every model accuracy against 0.9785." The shortcut also survives into the pixels: a frozen threshold on the decode scale factor (1024→256 is a 0.25 downscale for 100% of fakes, 4.0% of reals), fit on calib and applied to test, scores 0.9798. Whether the detector rides that laundered residue is an open problem named on the attacks page — the honest limit, not a solved one.

3 · Fitting on the split you then report

The lie: the number is good because the knob was tuned on the same data
A temperature, an abstention threshold, a decode cut-off — tune any of them on the test set and the test number improves for free and generalises to nothing. The rule here: fit on calib, freeze, apply to test. The moderation temperature (1.2785) is "fitted on ..._calib_clean and frozen" — stamped in the header of every condition table. The abstention policy is refit on each model's own clean calib at the 5% SLA, then frozen.

The evidence it is honest: the frozen policy's residual risk is 4.95% on calib and 4.65% on test — it generalises across the gap, which is only meaningful because the knob never saw test. See the moderation page.

4 · Oracle thresholds — peeking at the labels you're scoring

The lie: an abstention rule that quietly knows the answers
Selective-classification numbers depend on where the model abstains. Choose that operating point using the test labels — an oracle — and you report a risk no deployed system could achieve. The metrics module keeps the oracle only as a clearly-labelled reference (aurc_optimal_empirical, the empirical Bayes oracle for E-AURC), never as the operating policy. audit note the audit confirmed the oracle's gap to its closed form is exactly r/(2n) — i.e. the reference is right — and that the deployed threshold is the frozen-on-calib one from case 3, not the oracle.

5 · Batch-shape non-determinism verify.py

The lie: "accuracy is identical across every row" — off by one sample of floating-point weather
The headline of the confidence attack is that accuracy stays bit-identical at 0.8311 while ranking is destroyed. cuDNN convolutions are not bit-identical across batch shapes, so regenerating the clean row at a different batch size than the attacked rows moved accuracy by one sample in 15,316 — enough to make "identical" literally false. The margin noise floor from this effect is 8.31e-3; only 3 of 15,316 rows come back bit-identical.

The guard: verify.py requires every row for a given model and split to record the same batch, and fails otherwise. The fix is procedural, not statistical: regenerate every row at one batch size so "identical" is true by construction.

6 · The namespace collision that made a 512-row file verify.py

The lie: a debug run silently becomes the baseline
A quick --limit 512 run wrote its output to the same path as the full clean baseline and overwrote it. Now the "15,316-row" baseline held 512 rows, and every attack delta measured against it was against the wrong denominator. Nothing errored — the file was valid, just short.

The guard: the sidecar declares n and a uid-sequence hash; verify.py checks both against the manifest split and fails on n=512 where the split declares 15,316. This is the check whose absence caused the bug, added after it was found by eye.

7 · A theoretical bound that was FALSE where it mattered audit only

The lie: a passing test, on a fixture too weak to exercise its own claim
WP1's headline theorem is real: for a binary head, MSP = σ(|margin|/T) is strictly monotone in the margin, so temperature scaling cannot reorder samples and cannot move AURC, AUGRC or AUROC(failure). Test 8 asserts exactly this and passes. Test 9 ships the bound: "exact in float64 down to T = 0.5; breaks near T ≈ 0.2 when the softmax saturates." Both green. Both computed on a fixture with rng.normal(0, 2.5) — margins up to ~15.

The trained checkpoints produce margins up to 118.6. There, float64 saturates the softmax far earlier, and the "invariant" quantity moves. Recomputed from predictions_effb0_standard_..._overconf_..._s20.npz (verified for this page, CPU-only):

AURC moves 37.8e-3 — 9× the ~4e-3 the bound promised — the break is at T≈2.5, an order of magnitude above the stated T≈0.2, and inside the range declared exact. On the linear probes (max margin ~13) the invariance is genuinely bit-exact: AURC spread over T ∈ {0.5, 1, 2, 5, 10} is exactly 0.0 (verified). So the theorem is true; the numerical bound was calibrated to the wrong margins. The tell that catches it is n_op — the count of distinct operating points. At the reported T that cell already shows 12,661 of 15,316: the confidences are collapsing, and any cell with n_op < n is in the degraded regime where AURC depends on T. The corrected claim now says exactly that. See the harness page for the invariant, stated with its real limit.

8 · An under-optimised attack reading as robustness audit only

The lie: the defence held because the attack was weak, not because the defence was strong
"Adversarial training also protects confidence" rests on one epsilon of the over-confidence attack: PGD-AT's AUROC(failure) goes 0.8006 → 0.7770 and TRADES 0.7761 → 0.7789 (it goes up — an attack that improves the defender's failure-detection has not been shown to be at full strength). Three warning signs: (a) TRADES improves under attack; (b) a 4× smaller budget — ace_uint8 at ~0.96 grey levels — does 5× more damage (drops AUROC(fail) 0.135 on PGD-AT); (c) the attack's effective epsilon on PGD-AT is only 2.565 of 4.0 grey levels — 64% of budget with frac_perturbed = 1.0. An attack that fails to fill its own ball while touching every pixel is the textbook signature of gradient masking.

Status: this is now written as a question for the PIs, not a result. The under-confidence arm was never run; the attack is a fixed 20-step single-restart descent. Presenting a defence as proven on a possibly-masked attack is the kind of claim an adversarial-robustness reviewer takes apart in the room. See the defenses page.

9 · Printing AURC without the accuracy beside it

The lie: one number, two failure modes, and no way to tell which fired
Accuracy and ranking fail independently. An abstention metric printed alone hides which one broke.

If you print only AURC, the ACE row and the downscale row both look "bad" and you cannot see that one is a stealthy confidence attack holding accuracy fixed and the other is honest degradation. The rule: every table prints accuracy, AUROC(failure), AURC and n_op together. The audit's sharpest finding was that the README's own eight summary tables had dropped n_op — the one column that would have caught case 7.

Why the audit still mattered after everything was green

verify.py exits 0 (with four honest warnings about pre-dated CLIP feature sidecars). All 19 tests pass. And yet five independent audit passes — each recomputing every number from the .npz in float64, CPU only, told to "assume the author is capable and wrong somewhere" — logged 44 failing checks across five families. The one that indicts the automation itself
Case 7 was a passing test. verify.py's docstring even names the epoch-7/12-epoch sidecar lie as "already caught" — yet the audit found that exact sidecar (phase1_init.json, claiming 5,676 steps and 12 epochs for a run that stops at epoch 7) still sitting on disk. Naming a lie in a comment is not the same as having a check that fails on it. A green suite proves the lies you encoded are absent. It says nothing about the ones you haven't met yet — which is the entire job of the audit.

The ritual, in one paragraph

Recompute every number from the raw predictions, never from a previous table. Fit knobs on calib, freeze them, apply to test. Print accuracy, AUROC(failure), AURC and n_op in the same row, always. Carry the provenance line ("SID-Set validation slice, official test withheld") under every table. Split on the key that is actually unique. Read accuracy against the trivial baseline, not against chance. State each limit as plainly as each result. And keep one adversary in the loop whose only instruction is: the author is capable, and wrong somewhere.
