The dataset: SID-Set and its traps

Everything downstream — every accuracy, every attack, every defense — is measured on this data. If the data has a trapdoor, so does every number. It has two, and this page walks you into both so that no accuracy on this page ever looks better than it is.

The one sentence to carry off this page
On SID-Set an accuracy is not evidence of forensic capability until you read it against 0.9785 — a one-line metadata rule with no model in it — not against the 0.5 you would naively compare a coin-flip to. Every table in this project prints that baseline for exactly this reason.

What the data is

SID-Set is a public "Social-media Image Detection" dataset, pulled from HuggingFace as saberzl/SID_Set (cc-by-4.0, ungated). It ships three classes. Our binary task folds them to real vs fake: class 0 is real, classes 1 and 2 are both fake.

Within the fake class the two sub-tasks are not equally hard. On the CLIP probe, real-vs-synthetic scores AURC 5.47×10-3 while real-vs-tampered scores 19.63 — local edits are about 3.6× harder to catch than whole-image fakes (README.md results table). The interesting forensic curve lives in the tampered class; the shortcut below lives in both.

The shortcut that beats every model

SID-Set carries a geometry-and-format artifact so strong that a rule you could write on a napkin outscores every trained detector in this project. Measured on the exact test split (n = 15,316, 50/50 prior), from parquet metadata alone — no GPU, no model (src/baselines.py, runs/trivial_baselines.json):

The implication — this is the whole point of the page
The CLIP probe's 0.9289 is below the 0.9785 you get for free. Reporting 0.9289 as a success is reporting a number that a width == height check beats. So the honest reading of any accuracy on SID-Set is: the model earns credit only for the gap above 0.9785, not above 0.5. Read against 0.5 it looks like a strong detector; read against 0.9785 it is, on paper, losing to a napkin. This is a known dataset bias (Grommelt et al., "Fake or JPEG? Revealing Common Biases in Generated Image Detection Datasets"), and it is why the harness forces every table to print the baseline instead of quietly comparing to 0.5.

Where the shortcut lives: format and size, per class

The rule works because the label is almost perfectly encoded in the file's shape and format. All fakes are square; almost no reals are (runs/trivial_baselines.json):

classsquare (w==h)short side == 1024original PNG
0 — real4.3%4.0%0%
1 — synthetic100%100%100%
2 — tampered100%100%6.9%

Class 1 is 100% square 1024×1024 PNG; class 2 is 100% square; only ~4% of reals are square. The width == height rule mislabels only the roughly 4% of reals that happen to be square, which is exactly why it lands at 0.9785 rather than 1.0. Format leaks too: 100% of synthetic images were PNG and 0% of reals were, so "was it a PNG?" alone scores 0.7673.

Do our models ride the shortcut? The geometry control

Our detectors never see width and height — images arrive as 224×224 centre crops, so aspect ratio is discarded before the model. To prove the model isn't secretly reading geometry, we re-ran the CLIP probe under squarecrop: centre-crop every image to a square in both fitting and evaluation, which makes aspect ratio carry zero label information by construction (src/features.py::apply_condition, runs/condition_table_controlled.md).

Honest reading — this is a null result, not an exoneration

Accuracy barely moves (0.9289 → 0.9291), and it is tempting to call that "the model does not use the shortcut." It does not license that claim. Two confounds:

The control is a near no-op. squarecrop centre-crops to the shorter side, which is a bit-exact no-op on 100% of the fakes (they are already square), and both arms already feed the backbone a 224×224 centre crop — so aspect ratio was discarded either way. What this establishes: the model cannot read aspect ratio. What it does not establish: that the model is not riding the shortcut.

The shortcut is laundered, not removed. The decode cache re-encodes every image to JPEG q95, turning a PNG-vs-JPEG provenance difference into a single-vs-double compression trace a CNN can learn — plus a resampling history that cropping cannot touch. The evidence it survives: the decode-scale threshold (1024→256 = 0.25× for 100% of fakes, 4.0% of reals) still scores 0.9798 on the model's actual input pixels.

So it is an open problem. Whether the probe rides that laundered residue is unresolved. The settling experiment is named in src/baselines.py's own docstring and has not been run: evaluate on a format/compression-matched subset — pass every image through one identical JPEG re-encode, or restrict to real∩JPEG vs tampered∩JPEG — so that compression provenance carries no label information. This is a WP1 protocol change, and it is worth more than any accuracy point.

Trap two: img_id is not a key

19,107 img_ids appear in BOTH the train and validation splits

Synthetic and tampered images are numbered sequentially and the counter restarts per split, so full_synthetic_000155 exists in train and in validation as different bytes. A full 283-shard scan (runs/img_id_collisions.json) finds 19,107 colliding img_ids — 10,000 synthetic and 9,107 tampered. Every one of the 10,000 fully-synthetic validation img_ids collides with a train image.

The trap is that it fails silently: the real class is content-hash named and has zero collisions, so if you spot-check reals the problem is invisible. A flat feature cache keyed on img_id silently overwrites fit images with test images; a join between two npz files silently merges the wrong rows — leakage that raises your number and leaves no error.

The fix, enforced in the manifest: the real key is uid = "<source_split>:<img_id>". Everything joins on uid, never on img_id. This is why uid exists as a column at all.

Trap zero: this is validation, not test

Every number in this wiki is on the validation slice

The official SID-Set test split — 60k images — is withheld by the authors to prevent leakage. It is not on HuggingFace. Everything here is carved from the validation shards and labelled, in every sidecar, SID-Set validation split, held-out slice. Never call these numbers a "test set" result. If the authors grant the test set, re-running the manifest against it is about 20 minutes.

One further dataset property, not a protocol flaw: tampered images derive from COCO / OpenImages / Flickr30k and the dataset exposes no key linking a tampered image to its real source, so near-duplicate content can straddle any split and no split rule can prevent it. State this as a limit, not a fix.

A footnote that matters: the cache is lossy

The decode cache is stored at short-side 256, JPEG q95 (src/decode.py, runs/decode_report.json). That is fine for the CLIP/EffNet probes, which resize to 224 anyway, but it is the mechanism that launders PNG into JPEG — and it is unsuitable for any frequency-domain forensic detector, which is why the raw parquet is retained alongside the cache. Keep this in mind whenever a result seems to depend on compression: some of it may be the cache, not the image.
