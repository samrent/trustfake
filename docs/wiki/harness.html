The harness — metrics.py is the load-bearing artifact

The models are borrowed. The attacks are borrowed. What this project actually owns and ships is the thing that scores them: a data-agnostic scoring module and a strict file contract, so that every other subgroup's numbers pass through one code path and can never quietly disagree.

The one idea to keep
Think of the harness as a schema plus a referee, not a model. WP2 (attacks) and WP3 (defenses) each produce arrays. They hand those arrays to WP1, and WP1 turns them into the same twelve numbers every time. Because the referee never sees a model or a dataset — only (scores, labels) — an attacked run, a robustly-trained run, and a whole second dataset are all just different inputs to the same function. That is the entire design, and it is why src/metrics.py is the deliverable and the checkpoints are disposable.

The file contract — the npz, and why uid not img_id

Nothing in this project is trusted until it is written to disk in one exact shape. Every prediction — clean, attacked, or defended — is one .npz (a small zip of numpy arrays) plus a JSON sidecar of metadata. This is the interface published on Day 1, before any result exists.

runs/predictions/predictions_{model}_{split}_{condition}.npz
    uid     str          THE key: "<source_split>:<img_id>"   -- join on THIS
    img_id  str          dataset id, traceability only  (NOT unique -- see below)
    y       int8         0 = real, 1 = fake (synthetic OR tampered, folded together)
    label   int8         original 3-class label, so results can break out by difficulty
    logits  float32[n,2] [0, margin];   softmax -> p(fake) = sigmoid(margin)
+ JSON sidecar {model_id, manifest_sha, condition, split, seed, batch, timestamp, ...}

I loaded predictions_tf_efficientnet_b0_test_clean.npz to confirm the shape: fields uid, img_id, y, label, logits; logits float32 (15316, 2); y is int8 taking values {0,1}; and all 15,316 uids are distinct. A sample uid reads validation:tampered_07245.

Why the key is uid and never img_id
img_id looks like a unique identifier and is not one. 19,107 img_ids appear in both the train and validation splits — 10,000 fully-synthetic and 9,107 tampered — because those classes are numbered sequentially and the counter restarts in each split (runs/img_id_collisions.json). So full_synthetic_000155 exists in train and in validation as different images with different bytes. The real class is content-hash named and has zero collisions — which is the trap: spot-check a few reals and the problem is invisible. Keying a feature cache or joining two npz files on img_id silently merges the wrong rows and nothing errors. The fix is a compound key: uid = "<source_split>:<img_id>". See the dataset page for the full account.

condition is mandatory from line one. It is the label that says what was done to the pixels before the model saw them — clean, ace_uint8_eps0.005, jpeg_q50, pgd_linf_.... Without it, an attacked row and a clean row are indistinguishable strings in a folder, and the whole comparison is meaningless. It travels in the filename and the sidecar.

The metrics a newcomer needs — one at a time

The task is binary: real (0) vs fake (1). But a moderation pipeline does not just classify — it decides when to trust its own classification and when to route to a human. That second job needs a different family of metrics, and confusing the two families is the classic error this harness is built to prevent.

1. Accuracy (and F1) — did it get the label right

Plain top-1: fraction of images whose predicted class equals the true class. F1 is the same idea weighted toward the positive class (fake). These are the numbers everyone already knows. The harness prints accuracy beside every other number, always — for a reason that becomes the punchline below: some attacks leave accuracy untouched, so an accuracy-only test would call them harmless.

2. Two AUROCs — and conflating them is the cheap, embarrassing mistake

"AUROC" is not one number here. There are two, measuring two different questions, and a table that just says "AUROC" is ambiguous. metrics.py refuses to let them blur: they are separate functions with separate names.

AUROC(detection) Does p(fake) rank fake images above real ones? This is the classifier's core discrimination. 0.5 = coin flip, 1.0 = perfect. auroc_detection(p_fake, y). AUROC(failure) Does the model's confidence rank its correct answers above its own mistakes? This is the abstention question — can the model tell when it is about to be wrong. auroc_failure(conf, correct).

These come apart completely. The whole confidence-attack result (below) is a case where AUROC(detection) barely moves while AUROC(failure) is driven to near zero. On the clean CLIP probe, measured from the npz: AUROC(detection) = 0.9801, AUROC(failure) = 0.8898 — close by coincidence, and there is no reason they should track. A slide that reports one and calls it the other is the first thing a reviewer catches.

Worked intuition
A model that is 92% accurate has an AUROC(detection) near 1.0 (it separates fakes from reals well). Its AUROC(failure) asks a harder, orthogonal question: of the 8% it got wrong, was it at least unsure about them? A well-behaved model is under-confident exactly on its errors, so failure-AUROC > 0.5. An attacked model can be confident on its errors — failure-AUROC below 0.5, i.e. worse than a coin — which is the dangerous regime, because the abstention rule then throws away the correct answers and keeps the wrong ones.

3. The risk–coverage curve — the shape of selective prediction

A selective classifier is allowed to say "I don't know" and abstain. Two quantities trace out the trade-off, as a confidence threshold τ sweeps from strict to permissive:

coverage(τ)the fraction of images the model chooses to decide (does not abstain on). selective risk R_sel(τ)the error rate among the images it decided = Σ loss·[g≥τ] / Σ[g≥τ]. generalized risk R_gen(τ)the same errors divided by the whole set = Σ loss·[g≥τ] / n.

A good confidence signal means: as you lower coverage (abstain on more), selective risk falls (you kept the easy ones). The identity R_gen = coverage · R_sel holds elementwise — I confirmed it on the clean EffB0 curve to within 3e-17 (floating- point zero). That identity is the sanity anchor the whole curve is built on.

A subtlety that produces silent, fake numbers: tie blocks
Operating points exist only at distinct confidence values. If many images share the exact same confidence, a threshold that lands "inside" that block selects a set that depends on the sort order — not a property of the model. The trap: fp16/fp32 softmax saturates to exactly 1.0 for confident rows, manufacturing huge tie blocks silently. A naive cumulative AURC then swings by ~1.6e-2 across 8 permutations of the same predictions — an artifact the size of the effects being reported. metrics.py computes softmax in float64 and collapses tie blocks, so the curve is a property of the predictions and not of the sort permutation. n_op (the count of distinct operating points) is the tell-tale, and it returns as a guard below.

4. AURC vs AUGRC — one number for the whole curve, and why there are two

To rank models you want a single summary of the risk–coverage curve. AURC is the area under it — the (block-weighted) mean of selective risk across operating points. Lower is better. But AURC is dominated by its low-coverage tail, where selective risk divides by a vanishing denominator and the estimate rests on a handful of samples. AUGRC fixes that: it averages generalized risk (divide by n), which cannot blow up as coverage goes to zero. Measured on clean EffB0 from the npz:

metricvalue (×10⁻³)what it is
AURC67.05mean selective risk — tail-sensitive
AUGRC46.52mean generalized risk — tail-stable
AURC of the oracle ranker15.15same n, same errors, perfectly ranked
E-AURC = AURC − oracle51.91excess over a perfect ranker

For a random confidence signal, AURC ≈ error-rate r while AUGRC ≈ r/2 — they are not interchangeable and any table must say which it used, and with which weighting (this harness uses block-size-weighted mean over distinct operating points; the textbook mean-over-k and a trapezoid-over-coverage are different conventions that give different numbers). E-AURC subtracts the oracle so a perfect ranker scores exactly 0. One caution the code states outright: E-AURC still carries some dependence on the error rate, so it is a within-model diagnostic — cross-model claims ride on AUROC(failure), which is rate-free by construction.

5. ECE — is the confidence number honest (and why it is reported with company)

Expected Calibration Error asks whether a stated confidence of 0.8 actually means "right 80% of the time." It bins predictions by confidence and sums the gap between accuracy and confidence in each bin. Clean CLIP measures ECE = 0.0050. Two honesty caveats the code enforces:

  • Binning inflates it. A perfectly calibrated binary model still measures ~0.0056 at 5 bins, ~0.0102 at 15, ~0.0573 at 200 — the number depends on a knob. So the bin count and domain must be printed with it.
  • Binary MSP lives in [0.5, 1]. Equal-width bins over [0,1] leave 7 of 15 bins empty, making the number incomparable to a multi-class ECE. The harness reports both an equal-mass variant and a binary-domain variant.
  • Report NLL and Brier alongside — both are unbiased and binning-free, and unlike AURC they move under temperature scaling, which is exactly what makes them the right companions to the result in the next section.

The temperature-invariance result — in full, with the correction

This is the harness's sharpest theoretical claim, and it was corrected during the 19–23 Aug audit. Getting the correction right is the point: the clean version of the claim is true only on part of the system.

The claim
Temperature scaling (dividing logits by T before softmax — the standard recalibration trick) cannot change binary AURC, AUGRC, or AUROC(failure). Why: for two classes, the confidence is MSP = σ(|z₁ − z₀| / T) — the sigmoid of the logit margin divided by T. σ is strictly monotone, and dividing the margin by a positive constant does not change the order of the samples. Every risk-coverage metric depends only on that order. So temperature slides the operating point along a fixed curve; it cannot reshape the curve. Calibration therefore cannot rescue a confidence-based abstention rule — that is the deployment consequence.

Verified, bit-exact, on the linear probes. I re-scored the clean EffB0 probe at five temperatures. The margin here is small (max |margin| ≈ 11.9), so nothing saturates, and AURC is identical to every decimal place:

The correction: it breaks on the trained checkpoints
The invariance is only bit-exact when the logits are representable. The trained WP3 checkpoints are far more confident: under the over-confidence attack, effb0_standard reaches max |margin| = 118.6. At those magnitudes σ(|margin|/T) returns exactly 1.0 for large blocks of samples (float64 σ saturates once |margin|/T ≥ 36.74), manufacturing tie blocks — and inside a tie block the order is no longer defined, so the "order is preserved" argument no longer bites. At T = 1 the confidences have collapsed into a single tie block (n_op = 1): every sample has confidence 1.0, there is one operating point, and the AURC is a different number entirely. The invariance is real, but only where the margins are small enough that no two of them round together.
n_op is the guard — read it beside every AURC
n_op is the count of distinct operating points on the curve. If it is close to n (15,316 here), the curve is honest and the temperature-invariance holds. If it is far below n, the confidences have saturated into tie blocks and that cell's AURC is temperature-dependent and must not be read as a precise value. That is why the D3 defense tables print n_op in the same row as AURC. On the probes n_op sits at 15,264–15,268; on a saturated attacked checkpoint it can be 1. (One honest note: the run tables print this checkpoint's fitted-T n_op as 12,674; re-loading the stored npz for this page gives 12,668 — a few boundary samples, immaterial to the argument.)

The payoff the metrics were built to expose: two orthogonal failure modes

Read the top two rows together
The confidence attack leaves accuracy bit-identical (0.8311 → 0.8311) while driving AUROC(failure) from 0.7703 to 0.0471 — confidence now ranks the model's mistakes above its correct answers. An accuracy monitor sees nothing. The abstention layer, trusting that confidence, throws away the good decisions and keeps the bad ones. Contrast the bottom two: realistic corruptions destroy accuracy (0.83 → 0.68 under downscaling) while ranking survives (AUROC(failure) ≈ 0.70). These are two different diseases with two different symptoms, and only a harness that prints accuracy and failure-AUROC and AURC in every row can tell them apart. Print accuracy alone and the confidence attack is invisible; print AURC alone and you cannot say which disease you are looking at. The full threat-model treatment is on the attacks page.

verify.py — the referee needs its own referee

A scoring harness is only as trustworthy as the files it scores. src/verify.py is the self-consistency check you run before believing any table. Every defect it guards against actually happened in this repo, silently, and was caught by a human rather than by code:

  • a --limit 512 run overwrote the 15,316-row clean baseline with a 512-row file — every delta against it became meaningless, and nothing errored;
  • a checkpoint sidecar claimed a 12-epoch budget for a run actually cut at epoch 7;
  • the clean row was regenerated at batch 16 while the attacked rows were at batch 32 — cuDNN is not bit-identical across batch shapes, and it moved accuracy by one sample in 15,316, enough to break a headline that reads "accuracy identical across every row";
  • a mistyped condition parsed as a realistic row carrying a fabricated ε of 0.

So verify.py checks that every npz's uid sequence matches the manifest split it claims (by hash, not by trusting the filename), that dtypes and shapes hold (y is int8, logits is float32[n,2]), that no two comparable rows were produced at different batch sizes, that every condition string parses, and that no bulk artifacts (.pt, .npz, .parquet) leaked into git. It exits non-zero on any failure, so it lives in the pre-flight. Crucially, it guards the per-split uid sequence, not the manifest file hash — because manifest v1 and v2 share byte-identical calib and test splits and differ only in fit, so a whole-file hash would reject exactly the comparison WP3 needs while catching nothing real.

Why this is the load-bearing artifact
The models will be re-trained, the attacks re-tuned, the dataset possibly swapped for the official test set or for Munition-ID. Through all of it, the (uid, y, logits, condition) contract and the twelve functions in metrics.py stay fixed — so numbers produced by different people on different days remain comparable, and a self-consistency failure is loud instead of silent. That is the "reusable brick" the camp is meant to hand to the TRAIL Factory: not a detector, a referee.
